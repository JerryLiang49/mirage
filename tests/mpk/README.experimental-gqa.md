# Experimental paged GQA integration test

This test exercises the guarded, single-GPU cooperative paged decode path through the public graph and compilation APIs. It uses the SM100 partitioned implementation, eight independent requests, eight KV groups and eight query heads per group, head dimension 128, page size 64 and capacity 129 pages. It checks two adaptive producers (partition_tokens=4160) with and without sinks and one producer (partition_tokens=8256) with sinks. The two-producer path splits each request's visible interval at its midpoint rounded upward to a64-token page. The nominal chunk parameter selects this supported geometry, rather than a fixed4160-token runtime cut. Page alignment preserves unique append ownership; partial grouping can change rounded output values within the tested tolerance. A fourth case adds the supported dependent output projection and checks its full-activation dependency and numerical result. The oracle uses independent FP64 attention. It checks per-head output errors, all cache writes, input preservation, output guards, counters and repeated resets. Its purpose is correctness, not a speed claim.

Run the test only on a suitable SM100 device, with exactly one CUDA device visible and a working CUDA toolchain. It is expensive and opt-in. Launch it under a process timeout on shared systems because cooperative launches require adequate simultaneous device resources:

```sh
CUDA_VISIBLE_DEVICES=<device> MIRAGE_RUN_EXPERIMENTAL_GQA=1 timeout 1200s python -m pytest -v tests/mpk/test_experimental_paged_gqa.py
```

A cooperative launch can fail if resources are unavailable. Preserve the failure rather than silently changing launch mode. The test uses a manual producer-first schedule, not measured-cost search. Graph capture, ordinary noncooperative GQA launch, rank/exchange mode and profiling are unsupported by this cooperative path. Standard GQA measured-cost recording/reuse and the GQA build cache are disabled in this draft.

The guarded wrapper requires exclusive ownership of cache pages and caller ordering of metadata and KV updates through completion. Its process-local lease cannot prevent unrelated code or external processes from mutating bound tensors. Keep tensor storage, shape and strides fixed throughout the kernel lifetime. The test constructs private tensors; it does not prove synchronization safety against external concurrent writers or all shapes.

The test and its reference helper live together in `tests/mpk`. Run from that directory or use its repository-relative test path. Validation of this exact test is recorded separately with the candidate.

An additional opt-in `test_experimental_gqa_trajectory.py` validates three serialized advancing-decode trajectories: one 12-step fixed-page case reaching capacity and one 16-step sliding-window case that allocates, unmaps and reuses exclusively owned pages, and a three-step fixed-page case crossing lengths127,128,129. It checks each step against the same FP64 reference, exact full K/V cache contents, input preservation, guards and counters. These cases change Q, new KV and sinks between completed launches. Run them with the same device and opt-in settings, substituting `tests/mpk/test_experimental_gqa_trajectory.py` in the command above. These are correctness checks for the fixed supported shape, not performance measurements or tests of concurrent metadata writes.

The producer uses a local IEEE negative-infinity sentinel so valid finite negative logits do not collide with an empty state or retain initial denominator mass. An additional opt-in `test_experimental_gqa_logit_range.py` checks exact BF16 dot products below, at and just above the former finite sentinel, with mixed request lengths, windows and empty work. Run it with the same device and opt-in settings. Its constant values give a direct output control alongside the FP64 reference, full caches, readonly bytes, guards, counters and two repeated launches. This bounded test does not establish correctness for overflowing FP32 intermediates.
